# Tree Generation — Bug & Optimization Report

Scope: tree spawning, placement, canopy formation, and appearance in `voxEx.html`.
Date: 2026-06-13.

## How the system is structured (context for the findings)

Tree code lives in **two hand-maintained copies**:

- **Main thread** — `~4644–5475` (`TREE_CONFIG`, `resolveTreeProfile`, `getChunkTreePositions`, `generateTreesForChunk`, `forEachCanopyVoxel`), plus the mask at `~36348` and the cross-chunk leaf passes at `~16320–16470`.
- **Worker template string** (`CHUNK_WORKER_CODE`, starts `~17291`) — a parallel copy at `~17700–18192`.

Unlike the terrain functions (which are single-source — injected into the worker via `Function.toString()` between the `__TERRAIN_FUNCS__` markers), **the tree functions are NOT injected**. They are two separately edited copies, and they have drifted apart. That drift is the root cause of the most serious bugs below.

Placement is deterministic and cross-chunk: each chunk computes tree positions for itself and its 8 neighbors (`getChunkTreePositions`) and places whatever overlaps its bounds. Worker chunks always run with an empty `chunks` Map (`17706`), so the worker never validates neighbor trunks against real data — it trusts the deterministic generator and places canopies optimistically.

## Bugs

### BUG-1 — CRITICAL: worker and main-thread canopies are generated by different algorithms

`forEachCanopyVoxel` has diverged between the two copies in two independent ways:

**(a) Connectivity filter (PASS 2) is a completely different algorithm.**

- Main thread (`5394–5468`): a **flood-fill** from trunk-adjacent leaves using *extended* adjacency (6 face + 12 edge offsets). A candidate survives only if it is connected back to the trunk. Disconnected leaf clumps are deleted.
- Worker (`18071–18088`): a **single pass** — a candidate survives if **any one of its 6 face neighbors** is also a candidate (plus a special case keeping the single leaf directly above the trunk). No trunk-connectivity requirement.

These two filters produce **different leaf sets** for the identical tree. Worker trees keep detached 2-block leaf clumps and branch tips that the main thread's flood-fill culls; main-thread trees are strictly trunk-connected.

**(b) Branch-zone placement test differs.**

- Main thread (`5347–5358`): places a branch leaf if `dist <= effectiveRadius + 1.5`.
- Worker (`18034–18048`): places a branch leaf only if it has an 8-neighbor already inside `effectiveRadius` (`hasNeighbor`).

**Why it matters.** A tree whose canopy straddles a chunk border has its two halves placed by whichever generator built each chunk. When a tree's home chunk is worker-generated (single-pass canopy) but a neighbor re-places the overhang on the main thread (`placeNeighborTreeLeaves`, `16379`, flood-fill canopy), the two halves don't match — you get holes, doubled bumps, or asymmetric foliage **exactly along 16-block chunk seams**. It also makes generation non-deterministic with respect to *which path* built the chunk (worker vs main fallback), violating the project's parity contract (CLAUDE.md explicitly warns the worker tree code is a hand-maintained copy that must match).

**Suggested fix.** Make the tree code single-source the same way terrain already is. Move `forEachCanopyVoxel`, `getCanopyLayerRadius`, `getChunkTreePositions`, `generateTreesForChunk`, the tree mask, and their helpers into the main-thread single-source block and inject them into the worker template via `Function.toString()` between new `/* __TREE_FUNCS_START__ */ … __END__ */` markers in `buildChunkWorkerCode()`. This eliminates BUG-1 and BUG-3 at the root and prevents all future drift. If a full refactor is too large right now, the minimum fix is to **make the worker `forEachCanopyVoxel` byte-identical to the main-thread one** (port the flood-fill PASS 2 and the `+1.5` branch test) and add a regression test that diffs both canopy outputs for a fixed seed.

### BUG-2 — HIGH: tree-mask cellular automaton clips at chunk borders → 16-block grid gaps in forests

`generateTreeMaskForChunk` (`36348` main / `17755` worker) runs a 3-step cellular automaton **per 16×16 chunk**, and the neighbor count skips out-of-chunk cells:

```js
if (nx < 0 || nx >= w || nz < 0 || nz >= h) continue; // off-chunk = counted as 0
```

Because cells just outside the chunk are treated as empty, the CA's birth/survival rules behave differently on the 1-block border ring than in the interior. Trees are then looked up globally (`getTreeMaskValueGlobal`) from whichever chunk owns the coordinate. The result is a deterministic **grid artifact**: forest clusters get thinned or cut along every chunk boundary, producing faint rows/columns of missing trees on a 16-block lattice.

This is consistent between threads (so not a parity bug) but it's a visible quality bug.

**Suggested fix.** Compute the mask on a global lattice that includes a border margin. Either (a) generate the mask over an 18×18 (chunk + 1 ring) sample and crop to 16×16 after the CA, sampling `treePlacementValue`/biome for the ring cells too, or (b) drop the per-chunk CA entirely and replace clustering with a continuous noise field (`treePlacementValue` already warps with `noise2D`) thresholded globally — cheaper and seam-free. Option (a) is the smaller change and preserves the current clumping look.

### BUG-3 — MEDIUM: phantom-leaf pruning can't match worker-placed leaves

`prunePhantomNeighborLeaves` (`16419–16470`) removes the canopy of a neighbor tree that its own chunk rejected. It recomputes that canopy with the **main-thread** `forEachCanopyVoxel` (flood-fill, `16459`) and clears any `leafId` block at those positions. But the leaves it's trying to remove were placed by the **worker's** single-pass `forEachCanopyVoxel`. Per BUG-1 the two leaf sets differ, so:

- Worker-placed phantom leaves at positions the flood-fill *doesn't* produce are **never removed** → residual floating leaf bits at borders.
- The prune may also clear positions that belong to a *different* valid tree's overlapping canopy (the code comments acknowledge this as "rare, cosmetic").

This is a direct consequence of BUG-1; fixing BUG-1 (single-source) fixes BUG-3.

---

### BUG-4 — MEDIUM: trees over caves drop a floating canopy

Deterministic site validation (`isTreeSiteViable`, `4904` / `17886`) only uses `blendedHeight()` — surface height and slope. It cannot see caves, because cave carving is 3D noise applied after height. So a site directly above a cave passes deterministic validation; neighbor chunks (and the worker) optimistically place its canopy. When the home chunk actually generates, the trunk's ground/support check (`5111–5120`: `belowId === AIR` rejects "cave roof / overhang") **rejects the trunk** — leaving an orphaned canopy.

`prunePhantomNeighborLeaves` is the safety net, but it only runs on the main thread and is hampered by BUG-3, and it can't run until the neighbor chunk is actually loaded. Net effect: occasional floating canopies above cave mouths, sometimes persistent.

**Suggested fix.** Either (a) make the deterministic validator cave-aware — sample the same 3D cave noise used by terrain at the trunk base column and reject if carved (this makes the verdict consistent without needing chunk data, the same way slope is handled today), or (b) accept the optimistic placement but guarantee cleanup by also running a worker-side phantom check once neighbor data exists. (a) is cleaner and removes the orphan at the source.

---

### BUG-5 — LOW (tuning): multi-trunk longwood trees almost never spawn on natural terrain

`isTreeSiteViable` requires **every** trunk-footprint column to satisfy `h === groundY` exactly (`4913` / `17893`). For a 1×1 trunk this is a no-op (only the center, which is already `groundY`). But for 2×2 / 3×3 longwood trunks it demands 4–9 columns at the *exact same integer height*. On any undulating terrain that's rare, so giant trees become extremely sparse and tend to appear only on artificially flat patches.

**Suggested fix.** Allow a small tolerance for footprint columns (e.g. `Math.abs(h - groundY) <= 1`) and let the trunk base fill down to the lowest footprint column, or flatten/raise the base under the footprint. This makes giant trees feel intentional rather than accidental.

---

### BUG-6 — LOW: worker clears the tree-mask cache every chunk generation

The worker `onmessage` calls `treeMaskCache.clear()` on every `generate` message (`18351`). Since `getTreeMaskValueGlobal` is hit heavily during spacing competition (BUG-7/OPT-2), the mask for each chunk is recomputed from scratch repeatedly within a single chunk's generation and across adjacent chunks. The cache is keyed only by `cx,cz` (not seed), which is why it's being cleared defensively — but clearing every generation defeats the cache.

**Suggested fix.** Key the mask cache by seed (like `treePositionsCache` already is) and stop clearing it per-generation; clear only on seed change. Bound it with a simple size cap.

## Optimizations

### OPT-1 — Replace string-keyed maps in `forEachCanopyVoxel` (both copies)

The candidate set uses template-literal string keys and `key.split(',').map(Number)` to decode them (`5292`, `5368`, `5424`, `5442`, `18054`, `18074`). This allocates a string per candidate and re-parses on every neighbor probe — squarely the "string concat in loops → GC pressure" and "allocations in hot paths" anti-patterns called out in CLAUDE.md. Trees generate for the full 3×3 neighborhood of every chunk, so this runs thousands of times during streaming.

Fix: pack `(dx, y, dz)` into a single integer key (e.g. `((dx+32)<<16) | ((dz+32)<<8) | y`, ranges are tiny and bounded) and use a `Set<number>` / `Map<number>` or a small typed-array scratch grid. Removes essentially all per-leaf allocation.

### OPT-2 — `getChunkTreePositions` spacing competition is very expensive

The spacing loop (`4973–4988` / `17927–17938`) scans `(2·spacing+1)²` neighbors per candidate column and calls `wouldHaveValidTree` for each, which itself calls `getBiomeParams` + `getTreeMaskValueGlobal` (can trigger a full 16×16 mask + 3-step CA for a neighbor chunk) + `blendedHeight` + `getRiverFactor`. That's a heavy O(spacing²) of cache-cold work for every column of every chunk in the 3×3 neighborhood. This is the single biggest tree-gen cost.

Fix: precompute per-column `treePlacementValue`, biome, height, and river once per chunk into typed arrays, and have the competition read those arrays instead of re-deriving. Also short-circuit: the spacing radius is small (default 4), so cap the neighbor scan and skip the `wouldHaveValidTree` recomputation by reusing the candidate list already being built.

### OPT-3 — Dead variables

- `MAX_CANOPY_RADIUS = 8` is declared and never used in both `generateTreesForChunk` copies (`5048`, `18094`).
- `localX` / `localZ` (`5091–5092`) are computed and never used (placement uses `lx`/`lz` and `gx+cdx-startX`).

Remove them.

### OPT-4 — `treePositionsCache` does an abrupt full clear

When it reaches 512 entries it calls `.clear()` (`5036` / `17962`), dumping the whole cache and causing a recompute storm during continued streaming. Use a small LRU (or FIFO eviction of the oldest N) instead of clear-all.

### OPT-5 — `forEachCanopyVoxel` allocates several collections per call

Each invocation news up `candidates`, `connected`, `toProcess`, and `filtered` (main) or `candidates`/`filtered` (worker). With OPT-1's integer keys these can become reused module-scope scratch structures cleared between trees, removing per-tree allocation churn.

### OPT-6 — Mask CA temp buffer

`generateTreeMaskForChunk` allocates a fresh `tmp` `Uint8Array(256)` every call (`36367` / `17770`). With a module-scope scratch buffer (it's single-threaded within each context) this allocation goes away. Minor, but it's on the streaming hot path.

## Priority order

1. **BUG-1** (single-source the tree code) — fixes the most visible defect (mismatched canopies / border seams) and structurally prevents BUG-3 and future drift.
2. **BUG-2** (mask border clipping) — removes the 16-block forest grid pattern.
3. **OPT-2 / OPT-1** — the two biggest performance wins on the chunk-streaming path.
4. **BUG-4** (cave-roof canopies), **BUG-6**, then the remaining tuning/cleanup items.
